## Commands

- **Typecheck:** `npm run typecheck` (run `npm install` once first). It checks against the engine types Claude Code writes into `.claude-plugin/types/` whenever it loads the mod, so load the mod once (below) on a fresh clone or after a Claude Code update.
- **Single test file:** `claude plugin test` has no file filter; it always runs every `*.test.ts` under the folder. The whole suite takes about a second, so run it.
- **Full suite:** `npm test` (same as `claude plugin test .`).
- **Load in a session:** `claude --plugin-dir .` (hot-reloads on save). Then `/squishys` toggles the pane.
- **Art preview:** `npm run preview` writes `out/art-preview.html` (gitignored) from the current kit. Publish it as an Artifact with `capabilities: { db: {} }`; see "Art preview" below.
- **Validate before a PR:** `claude plugin validate .` (the marketplace) and `claude plugin validate .claude-plugin/plugin.json` (the manifest, hooks and `$.state` contract).

## Mod conventions

- `hooks/register.tsx` only wires features. Each feature is a module in `src/` exporting `register<Feature>(on)`. Pure modules (the roller, composer, roster layout) take plain data, never `$`, and their tests call them directly (with seeded randomness where they roll). Everything else is tested through the mod test kit in `tests/`, with shared inputs in `tests/fixtures.ts`. The third seam is the `SQUISHYS_FORCE_ROLL` environment variable, which forces what the mod's rolls come up as (docs/adr/0002-forced-rolls-env-seam.md; below).
- One hook per event per plugin: the engine refuses a second unmatched `on('tool.call')` anywhere in the module graph. A new behaviour on an event already hooked joins that event's existing hook. Where it needs `$` functions of another file, that file adds a matched hook instead, with a matcher every event fits (`src/agents.ts` hooks `session.start` with `{ isInteractive: [true, false] }`).
- The engine reads `$.state` references off each file statically, so every file that reads or writes a value declares its own `atom({ plugin: 'squishys', key }, initial)` const; an imported atom fails to load. Each value is declared in `types/index.d.ts`.
- Every `$.state.get` of one dispatch reads one moment, whatever is written meanwhile (the types say so), so a read after `await next(e)` misses what an event raised inside `next` wrote: a permission prompt during a `tool.call`, as `tests/needs-you.test.ts` shows. There, `src/agents.ts` keeps the `asking` set and calls `setState` with `current`, which writes without reading first.
- `$` is followed only into functions declared in the same file as the hook, never across an import. Logic shared between feature files takes plain data (as `settingsFrom` and `withModelDefault` in `src/settings.tsx` do), and the hook makes the `$` calls itself.
- Drawing hooks return `next(e)` unless `e.surface === 'terminal'`.
- The pane shows one mode at a time: the `mode` value in `$.state` (`PaneMode` in `types/index.d.ts`). Each mode is a feature module with its own `ui.render` hook on `{ component: 'Pane', requestId: 'squishys' }` (spelled out, so the engine can read the matcher) that draws only while `mode` names it and returns `next(e)` otherwise. Several matched hooks on one event are allowed. A new mode adds its name to `PaneMode` and a module like `src/settings.tsx`.
- A plugin's registrations nest in the order `hooks/register.tsx` makes them, first outermost, and features rely on it: the agent tracker comes before the focus view's feed hooks, so an agent first seen through a tool call is recorded before the feed looks it up, and the pane's render hook comes before every other mode's, so it can animate what they draw.
- Picking a squishy is one handler: the `ui.press` hook in `src/focus.tsx`, matched on `element: /^squishy-/`, answers a press on any pane or band Button keyed `${PICK_PREFIX}<agent id>` (`PICK_PREFIX` in `src/pane.tsx` is `squishy-`) by opening that agent's focus view; a press from outside the pane (`pickedOutsidePane(e)`: the band's) opens the pane too. A new place to pick from (the list opened from the overflow count, the band) keys its Buttons so and needs no handler of its own; their `onPress` stays a no-op. Beside it, not a second pick, `src/pane.tsx` has a matched `ui.press` hook on `{ plugin: 'squishys' }` that shuts the overflow list on any press but the overflow count's. The pane registers before the focus view, so its hook is the outer one: it shuts the list, then `next(e)` reaches the pick.
- The focus view's feed is a `StateFamily` (`activity` in `$.state`, one member per agent id, read as `atom({ ...activity, id }, [])`), so one agent's activity never redraws another's focus view. It keeps the latest `FEED_ROWS` rows and only the latest final answer; `fedAgentIds` lists the agents with a feed, so the feeds of agents the tracker no longer knows are emptied. Matched hooks in `src/focus.tsx` on `{ agentId: /./ }` fill it (and the rows of a run a redirect resumed, below). Thinking… is drawn from the agent's state, not kept in the feed. Text from an agent is made printable (no control characters but tab and newline) before it's drawn, since one control character makes the engine refuse the whole tree.
- Experimental features sit behind a setting that is off by default (absent from the stored settings until turned on) and whose label starts with "Experimental". The live model switch lives in `src/model-switch.ts`, which alone writes `switchedModels` in `$.state` (per agent: a `Model` alias and whether a request has gone out on it). The focus view only reads it and draws the model control (hotkey `m`, a Button with the element key `model-switch-<agent id>`, labeled by `modelControlLabel`: `model  <now> ▸ <next>`, the model it's on marked `(not allowed)` once the allowlist stops naming it). Label and press resolve the step the same way, through `modelStep` (`modelCycle(AS_STARTED, allowed)` from `src/settings.tsx`: as started, then each model `allowedModels` names; from a model no longer allowed, the next allowed after it in `MODELS` order). The drawing notes the step it drew (`noteModelStep`, a module variable), and the matched `ui.press` hook in `src/model-switch.ts` switches to what that label offered while the agent is still on what it was drawn from, so a model the allowlist stopped naming since is refused with a toast rather than skipped. It ends every switch by its own matched `ui.press` hook on the settings control `liveModelSwitch`, pressed while the setting is on. Its matched `turn.step` hook sits inside the tracker's and rewrites only a switched agent's requests (`next({ ...e, model })`, `effort` left out). Before each one it checks that the setting is on, the agent hasn't ended and the allowlist names the model, and ends the switch otherwise. A switch also ends with the agent's run and on `/clear`, `/resume` and a branch.
- The effort control sits under the model control, behind the same setting, and lives in the same two files: `src/model-switch.ts` alone writes `switchedEfforts` (per agent: an `Effort`, which mirrors the engine's `ModelEffort` since `types/index.d.ts` stays import-free; a type check in `src/model-switch.ts` fails if they drift) and `effortTaken` (per agent: whether its latest request, as the engine made it, carried an effort). It's a Button with hotkey `e` and element key `effort-switch-<agent id>`, labeled by `effortControlLabel` (`effort  <now> ▸ <next>` through as started, `EFFORTS` and back, or `effort n/a`), drawn while the setting is on and the agent runs, its press answered by a matched `ui.press` hook in `src/model-switch.ts`. Label and press resolve the step the same way, through `effortStep` (from those `$.state` values), and the drawing notes the step it drew (`noteEffortStep`), which the press follows while the agent is still on what it was drawn from. How the mod knows a model takes effort: the engine leaves `TurnStepInput.effort` out for a model that takes none, so the one `turn.step` hook notes, on every agent request before any rewrite, whether it carried one (written only as it changes), and `takesEffort` reads that (none seen yet counts as taken; the hook still checks each request). That signal describes the model the engine picked, never one the live switch moved the agent to, and nothing on `$` says which models take effort, so a switched agent counts as one that takes none: its requests carry no effort and the control says n/a, and a chosen effort stays and applies again once the model control is back on as started. The one hook does both rewrites: an unswitched agent with an effort chosen gets `next({ ...e, effort })` while its request carries one. The setting off (checked before each request, and its control's press), the agent's run ending, and `/clear`, `/resume` or a branch end its effort switch with its model switch, and clear its `effortTaken`, which its next request (a resume's) notes afresh; an allowlist refusal ends only the model switch, and that same request carries the chosen effort. Whether real requests honor the effort (and draw no 400) was not checked in a session; that's on the smoke test (#20).
- Model ids and the allowlist: the engine resolves an alias and checks it against the allowlist for `agent.spawn` and `$.model.complete`, but `TurnStepInput.model` promises neither, and nothing on `$` maps an alias to a model id (`$.session.model()` gives only the orchestrator's). `$.settings.read()` is an untyped record. So the switch sends an alias, and while Claude Code's `availableModels` setting is set, only an alias that setting names; an entry naming a full id allows no alias. Never hard-code model ids. Model controls step through `modelCycle` (`src/settings.tsx`), so they all order models the same way.
- Stop's rules and the agents it is stopping live in `src/stop.ts` (plain data). `src/focus.tsx` (the `ui.press` hook on `element: 'stop'`, and the note) and the agent tracker's hooks make the `$` calls. A press stops when it comes within `STOP_CONFIRM_MS` of the `armedAt` in `stopControl`, never by a timer, so an armed Stop survives a reload as harmless. The timer only redraws its note away. The hook awaits the `TaskStop` call inside its own dispatch: under the test kit, a `$.tool.call` the mod makes after its hook has returned skips the mod's own `tool.call` hooks. The tracker's hook is what makes the squishy of an agent `TaskStop` stopped Squished, once the agent list shows it ended. `TaskStop` names a teammate by its `teammateId` (or `name`), never its `id`. When `TaskStop` doesn't stop the agent, `holdBack` marks it: the tracker's `tool.call` and `turn.step` hooks (the outermost) refuse its tool calls and answer its next model request without the model. The marks change only in `setState`, as an agent ends or resumes, plus a `turn.step` of an ended agent (a resume) and a rebuilt session. Nothing the focus view draws about a stop is kept in `$.state`, so a reload leaves no stale note.
- A `Button` `hotkey` is one digit or one lowercase letter; the engine refuses anything else, so the spec's `,` for settings is `o`, and `r` returns to the roster. Every control in the pane has one (see "Keys" below).
- While an `Input` has the focus, every printable key goes to it alone (`InputProps` in the engine types; seen in a session for #13, where typing `r stop o 1` into the Redirect box pressed nothing). So the focus view keeps its hotkeys while the Redirect box is drawn, and the box takes no `autoFocus`: it would hold the keys whenever the pane takes them, and the hotkeys with them. The engine draws a colon after an `Input`'s `label` (seen in a session: `Redirect:` drew as `Redirect::`), so the Redirect box has no label: the redirect control beside it says `i: Redirect`.
- The keyboard in a pane, as seen in tmux sessions for #49 (Claude Code 2.1.289, both renderings): a pane with the keyboard and its ring on nothing hands any printable key that is no hotkey to the prompt, which types it there, so a hotkey whose control has gone (the model control's `m` once its agent ended) lands in the prompt. Tab walks the ring over the pane's Buttons and Inputs in drawing order. A click on an Input (fullscreen) gives the pane the keyboard with the ring on it; a click on a Button presses it without handing over the keyboard. Esc from an Input hands the keys back to the prompt, not to the pane, and Claude Code says nothing to the mod; given the keyboard again, the ring starts on nothing. So the redirect control (hotkey `i`, a Button with the element key `focus-redirect`, its press answered by a matched `ui.press` hook in `src/focus.tsx`) calls `$.ui.focus({ requestId: PANE_ID, key: 'redirect' })`, the Redirect box's element key, after asking for the keyboard (`askForKeyboard`, an `OPEN_PANE_ASKED` open while `$.ui.panes()` says the pane lacks it) for a click's press, and toasts a refusal. A pick in the pane asks for the keyboard the same way, so after a click on a squishy the focus view's hotkeys work at once. The focus view keeps where the ring is in a module variable (`ringOn`), set by a matched `ui.focus` hook and forgotten by any drawing without the keyboard, and the box's placeholder says `REDIRECT_HINT` ("Press i to redirect") while the pane has the keyboard and the box hasn't. The test kit has no implementation of a plugin's `$.ui.focus` (no test hook or inline plugin sees it, and it always rejects), so tests see the redirect control's call by its refusal's toast, without pinning the kit's reason, and move the ring as the person would, through the test's own `$.ui.focus`.
- A redirect goes to a running agent with `$.session.append` and to an ended one with `$.session.send`, which resumes it (`deliver` in `src/focus.tsx`). Both carry the text wrapped as the user's (`fromUser`), since a bare sent message reads to the agent as a peer's. The only fallback from append to send is a refusal for want of a running loop (Claude Code's `no running loop is <id>`). The test kit has no implementation of a plugin's `$.session.append`: no stub and no other plugin's hook reaches it, and it always rejects with `no implementation for session.append`. So the tests see a running agent's redirect refused, and the append itself was checked only in a session. The kit also drops an `Input` submit that no `change` came before, so tests type a `change` first.
- The run a redirect resumes hides from most of the mod's hooks. The engine types say only that a plugin's own call runs the chain with "the calling hook alone skipped" and "The calling hook alone is skipped, and `next.origin` names the caller" (`EventCalls`, `OpEventOf`). What happens to a loop that call starts was observed, not documented: in a tmux session for #60 (Claude Code 2.1.289, an extra debug plugin logging `next.origin`), every event of the agent's run that the mod's `$.session.send` resumed, all under the agent's own id, carried origin `squishys` where the run's own loop raised it, and none of those reached any of the mod's hooks. `turn.step`, `tool.call`, `classic.PostToolUse` and `classic.SubagentStop` were among them. `classic.SubagentStart`, every `session.append` row of its conversation (the message as door `prompt`, its response blocks as door `response`, tool results) and its `turn.complete` carried origin `engine` and reached the mod. A run the orchestrator resumes (SendMessage) carries `engine` throughout. The focus view marks an agent it resumes, in the plain module `src/resumes.ts` (`markResumed`, just before the send, which may start the run before it answers). The tracker's matched `session.append` hook (`{ agentId: /./, door: ['prompt', 'response'] }`) wakes an ended agent's squishy to Working (`stateAtRow` in `src/states.ts`) only for a redirect's run: while the agent is marked, or on a prompt row carrying the `fromUser` wrapper (`carriesRedirect`; Claude Code puts "The coordinator sent a message while you were working:" before it). Any other row after an end (one after Stop) changes nothing, and the hook calls `setState` (which lets Stop's marks and Needs you go) only when it wakes the squishy. Its `turn.complete` puts it back to sleep as after any run. No Thinking shows for such a run, since its stream is never seen. While the mark is on, the focus view's matched `session.append` hook on door `response` adds each `tool_use` block to the feed, as the `tool.call` hook does for any other run. The mark ends with the run however it ends (`setState`'s move to an ended state: `turn.complete`, `SubagentStop`, the agent list check, TaskStop), with a send that isn't delivered, on Back from an agent that shows ended, and on /clear, /resume and a branch (`forgetResumes`), so a later run's tool calls never show twice. Both hooks only read the row on its way down (before `next`; `tool_use` blocks are pinned, so no hook beneath can change them) and pass it on unchanged: nothing Claude Code delivers to the orchestrator changes. An agent may hand its report back through Claude Code's internal `SubagentHandback` tool, which leaves its run's `turn.complete` answer empty, so that call's `message` is the feed's answer row (`rowOfToolCall`), whichever way the call is seen. The kit has nothing beneath a plugin's `session.append` hooks to store a row, and such a hook can't answer without `next`, so the test's `$.session.append` always rejects after the mod's hooks have seen the row: tests raise rows with `appendRow` and `promptRowOf`/`toolUseRowOf` from `tests/fixtures.ts`.
- The latest redirect's delivery (`delivery` in `$.state`) shows in its agent's focus view until Back, a pick of another agent, or the agent ending (its `turn.complete`). One sent to a running agent also goes once its state shows it ended; one sent to an ended agent stays through the run it resumed, which starts as soon as the send is delivered. `/clear`, `/resume` and `/branch` reset it with every other `$.state` value.
- Lasting values live in `$.store` (settings under `settings`, each agent's squishy key under `agentSquishys`, the partner under `partner`, the Squishydex under `squishydex`; see below). The test kit leaves the store unanswered, and a hook whose store call goes unanswered is skipped, so every test that spawns an agent answers it with `mock.store(on)`, or with `stubStore(on)` from `tests/fixtures.ts` to read back what was saved.
- The pure modules (`src/kit.ts`, `src/roller.ts`, `src/composer.ts`, `src/raster.ts`, `src/states.ts`, `src/seeded.ts`, `src/slots.ts`, `src/verbs.ts`, `src/squishydex-record.ts`, `src/moments.ts`, `src/card.ts`, `src/png.ts`, `src/text.ts`, `src/keys.ts`, and the kit and card font data) never import from `claude-code`, so tools outside the mod (the art preview) use them as they are. Those are the only modules a tool may import; a tool never imports test code. The mod rolls with `cryptoRandom` from `src/roller.ts` (`crypto.getRandomValues`); tests and the art preview pass `seeded(n)` from `src/seeded.ts`.
- `claude plugin validate` wants `types/index.d.ts` self-contained (no imports), so a type it shares with a pure module (`Squishy`, `Rarity`) is written out in both. Change both together: the mod hands values both ways between them, so the typecheck fails if they drift.
- A squishy's state lives on its agent in the `agents` value (`state`), set by the agent tracker in `src/agents.ts`. The rules about states (which have ended, which move, which state an end maps to, what an answered prompt leaves) live only in `src/states.ts`. Every mode draws a squishy's picture through `animatedPicture(agent, size)` from `src/pane.tsx`, in a Raster keyed `pictureKey(agent.id, size)`, which draws it at the animator's current frame and has the animator repaint it; the pane's own render hook (the outermost) starts the animator after whichever mode drew. The band passes its own `e.requestId` as a third argument, so the animator blits to the band, and a matched `ui.render` hook on `{ component: 'AbovePrompt' }` in `src/pane.tsx`, outside the band's, starts the animator after the band drew. Animation frames only ever go out as `$.ui.blit` from the animator in `src/pane.tsx`: a frame never writes `$.state` or calls `$.ui.invalidate`.
- Mod tests read a squishy's state from its picture: `watch(ui, agentId)` (or `spawnAndWatch($)`) from `tests/pictures.ts` finds the squishy a just-spawned slot shows, and its `state()` names the pose the slot shows now, at any frame.
- The test kit drops the `key` of a `Text`: find a Text by `text`, or key the `Box` around it. It has no implementation of `$.ui.scroll` (a `ui.scroll` hook doesn't answer it), so wrap the call in `try` and don't test the scroll itself.
- `/clear`, `/resume` and `/branch` reset every `$.state` value to its default, and `session.start` doesn't fire again, but `classic.SessionStart` does, with `source` `clear`, `resume` or `fork` (the mods docs, "Load a saved value again after /clear": https://code.claude.com/docs/en/plugins/mods/interface#load-a-saved-value-again-after-clear). Compaction fires it with `compact` and keeps `$.state`. `src/rebuild.ts` rebuilds the roster on all four from `$.agent.list()`, each agent's state from `stateOfStatus` in `src/states.ts`, checking against the roster as it is inside its `update`. Each agent's squishy is kept in the store as `Remembered` pairs (`[agentId, squishyKey]`) under `agentSquishys`: only the key, which `squishyOf` in `src/roller.ts` turns back into the squishy, or nothing once the kit lacks a part. Every write to it goes through `rememberSquishys` in `src/rebuild.ts`, one queue per process that reads, merges and writes, with the hook passing its own store calls in (`StoreCalls`, below). Every session shares the store, so pairs are dropped by age past `REMEMBERED_AGENTS`, never for missing from one session's list. A feature with other `$.state` values to restore adds its own matched `classic.SessionStart` hook.
- Tests stand for `/clear` by firing `$.classic.SessionStart` (answered by `stubSessionStart`) without `session.start`: the kit starts every test with `$.state` at its defaults. `stubAgentList` takes a Map of statuses, or a list of agents with their own descriptions. `squishyIn(cells, name, state)` from `tests/pictures.ts` finds a squishy shown in any pose, as a rebuilt one may be.
- To check that none of the mod's hooks fails, `tests/rebuild.test.ts` loads `WATCHER`, an inline `prepend` plugin that toasts each squishys link `next.trace` reports as anything but returned or passed. An inline plugin's source runs apart from the test, so it shares no variables with it: everything it uses is inside `register`, and it reports through a call the test stubs.
- A spawn in a test rolls a random squishy (`SQUISHYS_FORCE_ROLL` forces only plain, shiny or legendary), so a test never assumes what a roll looks like. A roster slot's Button cuts a long Name (`slotLabel`), so a test that looks for the Name anywhere else reads it whole from the store with `nameOfAgent` from `tests/fixtures.ts`. That assumption failed about 1 run in 150 (#47).
- No test walks every squishy the kit can make, since the real kit makes thousands: cover every part once (`eachPart`), and keep spawns in a test to a handful.
- While a `turn.step` stream a test opened is still open, the kit waits out a timeout before each act (about 500ms for `find`, 1000ms for `clock.settle`). Read the first piece with `await stream.next()`, keep acts to a minimum until the stream is drained, and use `clock.advance`, which doesn't wait.
- Under `mock.clock` the agent list is checked every `AGENT_CHECK_MS` while any agent runs. A check that goes unanswered is skipped, so answer `agent.list` (`stubAgentList`) only where the test is about it. The kit can't reload the mod; a test stands in for a reload dropping the timers by refusing `clock.every` periods with its own hook (see the hot reload test in `tests/states.test.ts`).
- The roster layout is `layoutRoster` in `src/slots.ts`: the pane's placement, body columns and rows, the slot cap and the agents in; the agents in slots and the overflow out. The pane keeps the slots it last drew so squishys stay put. `squishysOnScreen()` in `src/pane.tsx` names those agents plus any other the pane last drew (the focus view's), and the agent tracker and the rebuild after /clear roll against `liveSquishys` (running agents plus those on screen), so an ended agent that is nowhere on screen returns its squishy to the pool. Which ended squishys give up their slots first (Asleep, then Squished) is `SLOT_GIVING_ORDER` in `src/states.ts`. Slot sizes derive from the composer's `PICTURE_SIZE` through `PICTURE_COLUMNS`/`PICTURE_ROWS`, and every gap the pane draws with is a named constant there; tests size a pane with `roomFor(placement, across, down)` and `paneSized` from `tests/fixtures.ts`, never with literal cell counts, and use `MAX_SLOTS` for the cap. Inline, Claude Code gives the pane only the rows the layout spares, and in tmux sessions for #55 (classic rendering, 120×35) that was 3 body rows, sometimes 2, though `/squishys` asks for `SLOT_ROWS`: the block shrank while the background-tasks list and spinner were up and didn't grow back on a resize, and reopened at 3 in a later session. So an inline pane's slots shrink before they go. `layoutRoster` gives a `slotSize` (`SlotSize`). It is `full` (the picture over the Name, description and mark) whenever a full slot row shows the partner and an agent. Otherwise it is whichever of `mini` (the mini picture beside those lines) and `label` (the Name's Button alone) shows the most squishys, `mini` on a tie. The pane draws every size through one table, `SLOT_SHAPES`. In an inline pane shorter than the footer's buttons are many, `footer` is `row`: the buttons lined up beside the slots, `FOOTER_ROW_COLUMNS` wide, so nothing scrolls at 1–2 rows. A docked pane's slots are always full. The animator keeps pictures by site and Raster key, so the pane's minis and the band's never stand for each other.
- The pane opens unasked at the session's first agent: the agent tracker's `assignSquishy` in `src/agents.ts`, whether the agent came through `agent.spawn` or the `tool.call` fallback, opens it with `OPEN_PANE` from `src/pane.tsx` (never `focus`) unless `$.ui.panes()` lists it already. Claude Code places such an open only from 144 columns (110 once the user has opened it before) and otherwise leaves it open but unplaced (`isPlaced` false). The band, `src/band.tsx`, draws only while the pane is unplaced, there are agents and `e.props.hasSurvey` is false, and returns `next(e)` otherwise. Which agents it shows and its overflow are `layoutBand` in `src/slots.ts` (pure, tested in `tests/slots.test.ts`): running ones first, then ended ones in reverse `SLOT_GIVING_ORDER`, as many as leave room for the "+N" and the hint, mini pictures from `BAND_PICTURE_ROWS` rows and the Names alone below. Its sizes derive from `PICTURE_COLUMNS` there. Band Buttons never carry a `hotkey`: a bare digit in an empty prompt presses a band Button, which would swallow the first keystroke of a message. `/squishys`, `/squishydex` and a pick from outside the pane (`pickedOutsidePane(e)` in `src/focus.tsx`: the band's) open the pane asked, so it's placed at any width. What makes an open asked is the person's input behind it, not `focus` (`PaneOpenArgs` in the types: "An open answering the person's input (a command or prompt they entered, a press) is placed at any width"). They open it with `OPEN_PANE_ASKED`, which adds `focus: true`; the first spawn's `OPEN_PANE` never does, so it can't take keys the user is typing. `focus` is "A request, not a grant: the surface focuses (and raises) the pane only while the prompt has the keys over an empty composer", and "An element of the band or a pane the person holds, text in the composer, a dialog or a survey each refuse it", so a band pick, whose press holds the keys, likely opens the pane without the keyboard. A refused open shows a toast (`openRefused`), and either way they call `$.ui.invalidate('ui.render')`, since nothing the band reads changes. Each open that goes through is noted by its args (`notePaneOpened` in `src/pane.tsx`, a module variable): only the asked opens carry `focus`. A command is typed at the prompt, which holds the keys meanwhile, so whether the pane has the keyboard says nothing when `/squishys` runs: it closes a placed pane once the user has asked for it since it last opened unasked, and otherwise opens it again with `OPEN_PANE_ASKED` (a reload only makes the next `/squishys` open it again first). `/squishydex` opens the pane again unless it's placed and has the keyboard. Band tests size the band with `bandSized` (`tests/band.test.ts`); pane, band and Squishydex tests stand in for Claude Code's panes (placement and keyboard) with `stubPanes` from `tests/fixtures.ts`.
- Keys and clicks: a pane's hotkeys work only while it has the keyboard (`isFocused` on the `Pane` props): opened with `focus`, or the user's Ctrl+X Tab or click. ## Keys

Words: a **hotkey** is the key a person presses (a Button's `hotkey`); an **element key** is the engine's `key` an element is drawn and matched under. Name a control by what it does (the redirect control, the model control), not by its hotkey.

Every control the pane draws answers to a single hotkey, shown in its label as `x: label`, and no two controls a mode draws at once share one; `tests/hotkeys.test.ts` holds each mode to it, past nine picks too. A choice among a few values is a Button that steps to the next value, labeled by `cycleLabel` (`name  now ▸ next`) with `nextOf` (`src/keys.ts`); no mode draws a `Select`. An `Input` is reached by a Button whose press moves the focus onto it (`$.ui.focus`). Picks in a row take `pickKeys(count, taken)`: the digits, then the letters the mode's other hotkeys leave free (`ROSTER_KEYS` in `src/pane.tsx`, `PAGE_KEYS` in `src/squishydex.tsx`, each built from the controls' own hotkey constants). Past those (32 picks in the roster's overflow list, 32 places on a Squishydex page, which only a very large pane holds) a pick has no hotkey and is reached by Tab and Enter, or a click under fullscreen rendering. Keep existing hotkeys where they are. A hotkey works only while the pane has the keyboard (opened asked, Ctrl+X Tab, a click under fullscreen rendering, or a pick in the pane). The band has no hotkeys by design (see the band above). A `Link` (Share's compose page) has none: it isn't a control, and the terminal opens it.

- Starter pick: `1`–`3` pick a starter.
- Roster: the squishys' slots by `pickKeys` (the partner `1`, then the agents), `m` the overflow count (`+N`), `o` Settings, `d` Squishydex. With the overflow list open, its agents take the digits in place of the slots.
- Focus view: `r` back to the roster, `s` Stop (twice), `1` the partner (back to the roster), `x` Share (while Asleep), `m` the model control and `e` the effort control (Experimental, while the agent runs), `i` the redirect control (moves the focus into the Redirect box; Enter sends, Esc hands the keys back to the prompt).
- Settings: `m` model for new agents, `s` roster slots, `l` Experimental live model switch, `c` chime (where offered), `r` back to the roster.
- Squishydex pages: the places met by `pickKeys`, `n` next page, `p` previous page, `r` roster. A species' card: `m` make partner, `c` partner palette, `x` Share, `b` back to the pages, `r` roster. A legendary's card: `b`, `r`.

## Art preview

- `tools/preview/` is development only and the mod never loads it. `items.ts` lists the items and draws them through `compose` and `roll` (tested in `tests/preview.test.ts`), `page.ts` writes the HTML, `client.js` is the page script, and `build.mjs` runs it all under Node's built-in type stripping, with a resolve hook that adds the `.ts` the mod's imports leave off. It imports only the pure modules, never `claude-code`.
- Item ids stay the same while the kit keeps its part ids: `body/<id>`, `face/<id>`, `palette/<id>` and `palette/<id>/shiny`, `accessory/<id>`, `sample/<squishy key>` (seed 1), the legendary's squishy key (`legendary/<id>`, `legendary/<id>/shiny`) and `starter/<body>/<face>`. Plain and shiny are separate items with their own verdicts.
- Verdicts live in the published page's database, collection `verdicts`, one document per item: `{ item, verdict: 'keep' | 'redo' | null, notes, art, updatedAt }`. `art` is the fingerprint (FNV-1a over the pixels, 8 hex digits) of the picture the verdict was given on. The page shows a verdict only while `art` matches the current picture; after a redraw the item reads "changed since your verdict" and counts as undecided. The document id is the item id with `/` as `:`, and any other character outside `A-Z a-z 0-9 _ - . @ +` (including `~`) as `~` and four hex digits of its code point. Read verdicts back with the `ArtifactData` tool (`list` on `verdicts`). Republish to the same artifact URL after redrawing, so the verdicts stay with the page. Deleting a document sets its item back to undecided.
- Opened without the database (as a local file), or after the store refuses a save, the page keeps verdicts in the browser with a notice, and shows them as JSON at its foot to paste back.
